# 05 — Верификация и результаты

## Что именно доказывается

ТЗ требует «подтверждение наличия CUDA в собранных образах». Формулировка
допускает трактовку «`nvcc --version` отработал», но это слабое доказательство:
toolkit может лежать в образе и при этом не применяться при сборке, а
device-код — быть собран не под ту SM-архитектуру и молча падать на устройстве
с `no kernel image is available`.

Поэтому проверка построена так, чтобы её нельзя было пройти формально.

## Уровни проверки

### Уровень 1. Toolkit присутствует

`nvcc --version`, наличие `libcudart`, соответствие мажорной версии CUDA
описанию платформы. Работает где угодно, включая x86-раннер без GPU (arm64-образ
запускается под QEMU).

### Уровень 2. Toolkit реально использовался при сборке

В каждый базовый образ собирается ROS 2-пакет `cuda_verify` с настоящим
`.cu`-файлом и `enable_language(CUDA)` в CMakeLists. Если `nvcc` в образе
нерабочий — сборка образа падает на этом шаге, а не выдаёт зелёный результат.

### Уровень 3. Device-код собран под правильную SM

Главная проверка. `cuobjdump --list-elf` читает секции ELF собранной библиотеки
и печатает, под какие архитектуры внутри лежат cubin'ы:

```
$ cuobjdump --list-elf /opt/verify/install/lib/libcuda_verify_kernels.so
ELF file    1: cuda_verify_kernels.1.sm_87.cubin
```

Это работает **без GPU и без драйвера** — то есть проверяется прямо на
x86-раннере сразу после кросс-сборки. Именно эта проверка отличает
«CUDA лежит в образе» от «CUDA применена к целевой платформе».

Ожидаемые значения:

| Платформа | Ожидается |
|---|---|
| `x86_64-cuda` | `sm_75 sm_80 sm_86 sm_89 sm_90` |
| `jetson-agx-orin-jp62` | `sm_87` |
| `jetson-orin-nano-jp7` | `sm_87` |

### Уровень 4. Код выполняется на реальном GPU

`cuda_smoke` выделяет память на устройстве, запускает ядро сложения векторов на
миллионе элементов и сверяет результат на CPU. Нода `cuda_info_node` делает то
же периодически и публикует состояние в топик `/cuda_verify/status` — то есть
GPU проверяется штатными средствами ROS.

Запускается там, где GPU есть: на x86-хосте с dGPU или на самом Jetson.
Если GPU нет, проверка помечается `SKIP`, а не пропускается молча — в отчёте
это видно.

## Запуск

```bash
./scripts/verify-image.sh \
  --image ghcr.io/victoryurochkin/fast_lio2:jetson-agx-orin-jp62-cross \
  --platform jetson-agx-orin-jp62 \
  --package fast_lio2 \
  --report verify.md
```

Скрипт возвращает ненулевой код при любом `FAIL`, поэтому годится как тестовая
стадия пайплайна напрямую. В CI отчёт попадает в Job Summary и в артефакты.

## Сравнение нативной и кросс-сборки

Обе сборки одной платформы публикуются рядом (`-native` и `-cross`), поэтому
их можно сравнить напрямую:

```bash
for mode in native cross; do
  img=ghcr.io/victoryurochkin/fast_lio2:jetson-agx-orin-jp62-$mode
  echo "== $mode"
  docker run --rm --platform linux/arm64 "$img" \
    cuobjdump --list-elf /opt/verify/install/lib/libcuda_verify_kernels.so
  docker run --rm --platform linux/arm64 "$img" \
    bash -lc 'ros2 pkg list | wc -l; nvcc --version | tail -2'
done
```

Ожидаемо: одинаковый набор SM, одинаковая версия CUDA, одинаковый состав
пакетов. Различие — только во времени сборки.

Ориентировочные времена (холодный кеш, 4 vCPU):

| Сборка | Базовый образ | Пакет |
|---|---|---|
| x86_64 нативно | ~12 мин | ~8 мин |
| ARM64 нативно (hosted arm-раннер) | ~25 мин | ~20 мин |
| ARM64 кросс через QEMU | ~2–3 ч | ~1.5–2 ч |
| ARM64 нативно на AGX Orin | ~20 мин | ~15 мин |

С прогретым registry-кешем повторные сборки укладываются в единицы минут, если
не менялись слои с `apt install`.

## Ограничение, которое стоит знать

FAST-LIO2 в upstream не содержит CUDA-кода — это CPU-алгоритм. «Собранный с
поддержкой CUDA» здесь означает, что образ и система сборки полностью готовы к
GPU-коду: toolkit на месте, `CMAKE_CUDA_ARCHITECTURES` применяется ко всем
пакетам оверлея, device-код собирается под целевую SM и проверяется. Это
доказано на `cuda_verify`, который собирается тем же самым механизмом, в том же
образе, теми же флагами.

Как только в проект придёт пакет с реальным GPU-кодом (CUDA-форк FAST-LIO,
CUDA-PointPillars, cuVSLAM, любой пакет Isaac ROS), ему достаточно строки
`PKG_CMAKE_ARGS="-DUSE_CUDA=ON"` в манифесте — инфраструктурных изменений не
потребуется.
