# 01 — Архитектура и обоснование решений

Документ отвечает на вопрос «почему сделано именно так», а не «как этим
пользоваться» (это в [02-deployment.md](02-deployment.md)).

---

## 1. Различия платформ

| | x86_64 + dGPU | AGX Orin (JP 6.2.2) | Orin Nano (JP 7.2) |
|---|---|---|---|
| Архитектура | x86_64 | aarch64 | aarch64 |
| GPU | дискретный, своя VRAM | интегрированный, память общая с CPU | интегрированный |
| L4T | — | R36.5.0, ядро 5.15.185-tegra | R39.2, ядро 6.8 |
| rootfs | любой | Ubuntu 22.04 | Ubuntu 24.04 |
| CUDA | 12.x/13.x, ставится в образ целиком | 12.6, часть библиотек монтируется с хоста | 13.2, то же |
| Compute capability | 7.5–9.0 | **8.7** | **8.7** |
| Драйвер | `nvidia-container-toolkit`, `--gpus all` | `nvidia-container-runtime` (L4T), `--runtime nvidia` | то же |

Практические следствия:

* **Один и тот же `CMAKE_CUDA_ARCHITECTURES` не подходит всем.** Для Orin это
  `87`. Сборка «на всякий случай под всё» раздувает бинарник и время сборки
  кратно, поэтому SM задаётся по платформе в `platforms/*.env`.
* **Jetson не самодостаточен внутри контейнера.** Библиотеки, привязанные к
  железу (`libnvidia-*`, драйвер, мультимедиа), NVIDIA Container Runtime
  монтирует с хоста в момент запуска. Класть их в образ нельзя — при
  несовпадении версии с BSP хоста контейнер сломается. Поэтому в базовых
  Jetson-образах ставятся **только dev-компоненты** (CUDA Toolkit, cuDNN dev,
  TensorRT dev), а `nvidia-l4t-*` сознательно не устанавливаются.
* **Версия CUDA в образе должна быть ≤ версии драйвера на устройстве.** Именно
  поэтому нельзя взять образ с CUDA 12.6 и запустить его на JetPack 7: там
  драйвер CUDA 13, обратная совместимость есть, прямой — нет.

## 2. Выбор базовых образов

### Почему не `nvcr.io/nvidia/l4t-jetpack`

Очевидный путь — взять готовый образ NVIDIA. Он не работает:

* последний опубликованный тег `l4t-jetpack` — `r36.4.0` (это JetPack 6.1).
  Под `r36.5.0` (JP 6.2.2) образа нет; под `r38.x`/`r39.x` (JetPack 7) базовых
  образов NVIDIA тоже нет — на форуме разработчиков это подтверждено, людям
  предлагают использовать DLFW-контейнеры (vLLM, TensorRT) или общие
  `nvcr.io/nvidia/cuda` для arm64/SBSA;
* образ весит ~8 ГБ, из которых нам нужен CUDA Toolkit и заголовки;
* версия CUDA в нём жёстко зашита и не совпадёт с устройством, если на нём
  другой JetPack.

### Что сделано вместо

Базовый Jetson-образ собирается из `ubuntu:22.04` / `ubuntu:24.04` плюс
**официальный apt-репозиторий Jetson**:

```
deb https://repo.download.nvidia.com/jetson/common <suite> main
deb https://repo.download.nvidia.com/jetson/t234   <suite> main
```

где `<suite>` — `r36.5` для JP 6.2.2 и `r39.2` для JP 7.2, а `t234` — SoC
семейства Orin. Это ровно те репозитории, которые SDK Manager прописывает на
самом устройстве, поэтому версии совпадают с целевым железом гарантированно, а
не «примерно».

Один тонкий момент: postinst-скрипты L4T-пакетов читают `/etc/nv_tegra_release`,
чтобы определить версию BSP. При сборке контейнера на x86 этого файла нет и
установка падает. Файл создаётся вручную перед `apt install` — это стандартный
приём для сборки Jetson-образов на десктопе.

Альтернативный путь (наследование от `l4t-jetpack:r36.4.0`) поддержан: в
`platforms/jetson-agx-orin-jp62.env` достаточно заменить `BASE_FROM` и
`BASE_DOCKERFILE`. Он оставлен как запасной, но не как основной.

### x86_64

Здесь всё просто: `nvidia/cuda:12.6.3-devel-ubuntu22.04` — официальный образ с
полным toolchain. Собирать самому нечего.

## 3. ROS 2 на JetPack 7

Это единственное место, где ТЗ вступает в противоречие с реальностью, и его
стоит проговорить явно.

**ТЗ требует ROS 2 Humble на всех трёх платформах.** Humble привязан к Ubuntu
22.04 (jammy): бинарных пакетов под noble нет и не будет — ROS 2 привязывает
дистрибутив к конкретному релизу Ubuntu на весь срок поддержки. JetPack 7
построен на Ubuntu 24.04.

Варианты и их цена:

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **A. ROS 2 Jazzy из apt** | ставится за минуты, поддерживается, тот же API rclcpp | не Humble; пакеты, прибитые к Humble, могут потребовать правок | **выбран по умолчанию** |
| **B. Humble из исходников на noble** | формально соответствует ТЗ | 40–60 мин нативно и кратно дольше под QEMU; часть зависимостей на noble требует патчей; нет обновлений безопасности из apt | поддержан флагом `ROS_BUILD_MODE=source` |
| **C. Контейнер на jammy поверх ядра 6.8** | Humble из apt, userspace развязан с ядром | внутри окажется CUDA 12.6 при драйвере CUDA 13 на хосте — GPU теряется, а именно ради GPU всё и делается | отвергнут |

Переключение между A и B — одна переменная в `platforms/jetson-orin-nano-jp7.env`:

```bash
ROS_BUILD_MODE="source"
ROS_DISTRO="humble"
```

Рекомендация: для реальной эксплуатации на JP 7 переходить на Jazzy, а Humble
оставить для JP 6.2.2. Вариант B имеет смысл только как переходная мера, пока
прикладные пакеты не портированы.

## 4. Нативная сборка vs кросс-сборка

Реализованы оба способа (п. 3.4 ТЗ).

### Кросс-сборка через QEMU

`docker buildx` + `binfmt_misc` с зарегистрированным `qemu-aarch64`. Хост x86,
целевая платформа `linux/arm64`. Работает на любом раннере, не требует ARM-железа.

Важные детали, которые ломают сборку, если их не учесть:

* **Версия QEMU.** В `tonistiigi/binfmt` до `qemu-v8.1.5` встречались ошибки
  трансляции, из-за которых `nvcc` и сборка PCL под aarch64 падали с
  `uncaught target signal 11`. Версия зафиксирована в `scripts/setup-qemu.sh`.
* **Параллелизм.** Эмулируемая сборка потребляет память кратно больше нативной.
  `-j$(nproc)` на 4-vCPU/16-ГБ раннере приводит к OOM-killer посреди сборки PCL.
  В режиме `cross` `PARALLEL_WORKERS` по умолчанию равен 2.
* **Скорость.** Под QEMU сборка идёт примерно в 5–15 раз медленнее нативной —
  это цена независимости от ARM-железа.

### Нативная сборка на ARM-раннере

Два варианта, оба поддержаны:

1. **Hosted-раннеры GitHub** — `ubuntu-22.04-arm` и `ubuntu-24.04-arm`. С августа
   2025 они общедоступны и бесплатны для публичных репозиториев (4 vCPU,
   Cobalt 100 / Neoverse N2). Это настоящий aarch64 без эмуляции, сборка идёт в
   разы быстрее QEMU. GPU на них нет — но для *компиляции* CUDA-кода GPU и не
   нужен, `nvcc` компилирует device-код без устройства.
2. **Self-hosted раннер на самом Jetson** — метки вида
   `self-hosted,jetson,agx-orin,jp62` уже прописаны в `platforms/*.env`.
   Единственный вариант, где к сборке добавляется рантайм-тест на реальном GPU.

Разделение обязанностей получилось такое: базовые образы собираются один раз
(по умолчанию нативно на ARM-раннере, это быстрее), а образы пакетов — обоими
способами, с разными тегами `-native` и `-cross`, чтобы результаты можно было
сравнить.

## 5. Почему `.env`-файлы, а не YAML

Описания платформ и пакетов — обычные shell env-файлы. Причина прагматичная:
их без парсера читают и `source` в bash-скриптах, и шаг генерации матрицы в
GitHub Actions, и `docker build --build-arg`. YAML потребовал бы `yq` или
Python с PyYAML на каждом раннере и в каждом контексте. Формат `KEY="value"`
покрывает 100% потребности и не добавляет зависимостей.

Следствие: **добавление платформы или пакета — это добавление одного файла.**
Ни Dockerfile, ни workflow не меняются, матрица CI формируется из
`platforms/*.env` динамически.

## 6. Кеширование

Используется registry-кеш buildx:

```
--cache-from type=registry,ref=<image>-cache
--cache-to   type=registry,ref=<image>-cache,mode=max
```

Почему не `type=gha`: кеш GitHub Actions ограничен 10 ГБ на репозиторий, а один
слой с CUDA Toolkit под Jetson занимает 3–6 ГБ. Трёх платформ хватает, чтобы
кеш вытеснился на первом же прогоне. Registry-кеш живёт в том же ghcr.io, не
имеет такого лимита и общий для всех раннеров.

`mode=max` сохраняет промежуточные слои, а не только финальный — для сборок,
где 80% времени занимает `apt install`, это принципиально.

Дополнительно внутри Dockerfile используются `--mount=type=cache` для
`/var/cache/apt` и `/root/.ccache`: они переживают перезапуски сборки на одном
раннере и заметно ускоряют итерации при отладке.

## 7. Что считается «поддержкой CUDA» у собираемого пакета

Отдельно стоит проговорить, потому что здесь легко себя обмануть.

FAST-LIO2 в upstream — **CPU-алгоритм**: ikd-Tree и итеративный фильтр Калмана
считаются на хосте, CUDA-кода в репозитории нет. Собрать его «с поддержкой
CUDA» в смысле «алгоритм поедет на GPU» невозможно без форка. Поэтому
«поддержка CUDA» в этой системе означает три конкретные, проверяемые вещи:

1. в образе присутствует и работоспособен полный CUDA Toolkit (`nvcc`,
   заголовки, `libcudart`) нужной версии;
2. сборка ведётся с `CMAKE_CUDA_ARCHITECTURES`, заданным для целевой платформы,
   и он применяется ко **всем** пакетам оверлея — любой пакет с
   `enable_language(CUDA)` соберёт device-код под правильную SM без правок;
3. это подтверждается не декларацией, а `cuobjdump` по собранному бинарнику.

Для проверки пункта 2 в состав образа входит пакет `cuda_verify` с настоящим
`.cu`-ядром. Если в проект придёт CUDA-форк FAST-LIO (или любой другой пакет с
GPU-кодом), ему достаточно указать `PKG_CMAKE_ARGS="-DUSE_CUDA=ON"` в манифесте —
инфраструктура уже готова.
